Workspace TTL: 4h example

Automatic expiry and rotation
  • Workspace, Auto permission, sandbox token and model session: expire by the user-set workspace deadline. Activity and token refresh never move it. Four hours is illustrative.
  • Approvals: short-lived, single-operation, exact parameters; unusable after their deadline, a policy change or workspace expiry.
  • Current Convex key: no native API-key TTL. The binding expires and ciphertext is erased. Upstream revocation needs browser auth; pending cleanup is retained. The environment encryption secret is not a separate KMS boundary.
  • Earlier KMS/expiring-key proposal: absolute expiry no later than the workspace. Native API enforcement is required; until available, control-plane denial and revocation cleanup are the fallback.
  • Auto-mode OAuth: access tokens last one hour in this model. Refresh access has a finite connection deadline; rotating tokens does not reset it. Workspace expiry blocks this workspace even if the account connection is still valid.
  • Browser sessions, codes, assertions and service authentication: keep their issuer's expiry. Interactive requests reuse a valid browser JWT; the browser renews it before expiry. The earlier JWT-only design stores no user API key; the current Convex design does. Protected service keys rotate independently; retain old decryption versions only while valid ciphertext needs them.
  • Data and compute: purge chat/activity history after 28 days. New agent-created compute gets an explicit auto-stop lifetime; deployments have their own deadline, and existing resources are untouched.
